1 Executive summary

Tholos is a local-first, offline-by-design Electron notebook (React renderer, Node main process, SQLite store) with two optional security-relevant features: per-section encryption at rest (“Locked Sections”) and a local MCP server that lets an AI coding agent (e.g. Claude Code) read and write explicitly allowlisted notes.

The trust model in three sentences: the machine's OS user account is the trust boundary — any same-user process is assumed benign except where encryption extends protection to data at rest. All content (notes, pasted clipboard data, imported documents, indexed corpora) is treated as untrusted input. The AI agent is treated as a confused deputy: potentially hijacked by injected content, so the tool surface it reaches is capability-scoped and structurally unable to execute code or reach the network.

  • Runtime network egress is a single, well-defined channel: the update check against GitHub Releases. Nothing else in the packaged app touches the network — fonts are bundled, embeddings run from a local model pinned offline, and there is no telemetry of any kind. Re-validated 2026-08-24 after the Savings Ledger shipped: still true as a claim about network channels opened by application code, with a category distinction now stated explicitly — user-directed file writes (export save dialogs; the opt-in scheduled Savings Report) open no socket, though a user-chosen network-backed destination (a UNC share) makes the OS carry that write over the network at the user's direction, and a synced folder is moved afterwards by the user's own sync client. The safety property in every case is that the written content is content-free by construction (§4.4).
  • The MCP surface satisfies Meta's Rule of Two with a structural argument, not a policy one: the server exposes zero network-capable and zero code-executing tools, so the “external communication” leg cannot be closed from inside Tholos (§5).
  • The memory-poisoning channel (§5.4, F-3's residual) is no longer stealthy or irreversible (ADR-0021): memory provenance is server-stamped evidence rather than an agent claim, every agent Persona rewrite is snapshotted, flagged in the main window, and restorable, memory/persona writes get the same external-link flagging as Pages, forgetting is recoverable for 30 days, and recall returns as fenced stored data. Persistence itself remains inherent to agent memory — the mitigations are attribution, visibility, and recovery, not prevention (§5.4).
  • The cryptography is a small, sound core: AES-256-GCM + Argon2id at OWASP parameters, keys confined to main-process memory and zeroized; the improvements this review identified — envelope versioning, AAD address binding, residue scrubbing — are now implemented as envelope v2 (ADR-0019, F-2 remediated, §6).
  • Release integrity (F-1) is remediated: releases are CI-built and staged as drafts, Windows installers are Authenticode-signed during packaging via Azure Trusted Signing (short-lived certificates over repo-federated OIDC — no signing key exists to steal), and shipped binaries validate their asar against a hash embedded at build time (Windows/macOS). Documented residuals, all Linux-shaped: no asar validation (dpkg checksums only), no independent .deb signature (update-channel integrity there rests on HTTPS plus a sha512 manifest shipped from the same feed), and on Windows the unpacked set is covered by the installer signature rather than the asar hash.

3.3 Security objectives (STEAM)

Each objective names the Threat violated, the Entry point / Attacker, the Asset, and a Measure of required strength.

  • O1MetLocked Section content (S1) must not be recoverable in plaintext by an attacker with full read access to the on-disk database (A2/A3), withstanding offline brute force to the strength of AES-256-GCM under Argon2id-derived keys at ≥ OWASP-recommended parameters with a random 16-byte per-section salt. Pre-lock plaintext residue is scrubbed after the lock transition (F-2 remediated, ADR-0019); filesystem-level remanence remains out of userland reach.
  • O2MetSection Keys and passphrases (S2) must not be disclosed to a compromised renderer (A1): keys exist only in main-process memory, are zeroized on lock/relock/quit, and never cross IPC — only decrypted content returns.
  • O3MetMalicious note content (A1 via the Preview) must not achieve code execution or host file access, to the combined strength of the Chromium sandbox + contextIsolation + no nodeIntegration + strict CSP + html:false markdown rendering with dangerous-scheme link filtering.
  • O4MetThe renderer must never name a filesystem path: every path originates in a native dialog or a main-issued single-use opaque token, with export filenames sanitized.
  • O5MetA prompt-injected agent (A6, composed from A1) must not exfiltrate notes/memories or execute code through Tholos, to the strength of structural absence: zero network-capable and zero code-executing tools, verified by the enumeration in §5.2.
  • O6MetThe MCP HTTP endpoint must reject any caller without the bearer token: a 256-bit random token compared in constant time before any dispatch, on a loopback-only socket with DNS-rebinding protection and no CORS.
  • O7MetLocked Sections must be unreachable through the agent surface regardless of configuration mistakes, by construction: the agent gateway is built with no key session, so it cannot decrypt even if asked.
  • O8PartialThe auto-update channel must not allow substitution of a malicious installer. Met on Windows: HTTPS + sha512 pinning, CI-built draft-staged releases with signing mandatory for tag builds, Authenticode signing via Azure Trusted Signing (OIDC-federated, no exportable key). Weaker on Linux: the .deb carries no independent signature and its sha512 manifest ships from the same feed — feed compromise (A4) replaces both together. Documented F-1 residual.
  • O9MetCode shipped to users must match reviewed source: sha512-integrity lockfile, 7-day cooling-off window, per-package build-script approvals, guarded installs, pinned model digests, and embedded asar integrity validation on Windows/macOS — the installer signature is the unpacked set's tamper evidence (F-1 remediated; Linux asar validation remains a documented gap).
  • O10MetParsers of untrusted bytes must not crash or hang the app, demonstrated continuously by two-tier fuzzing in CI — property suites on every PR plus coverage-guided nightly runs (§9).
  • O11MetUser content must not leave the machine at runtime: zero runtime egress besides the update check — fonts self-hosted, embedding model bundled and pinned offline, no telemetry, remote images in notes blocked by CSP. User-directed file writes (§4.4) are outside this objective by definition — the user moves their own bytes; the Savings Report additionally carries no content (S9, ADR-0022).

3.5 Accepted risks

  • Same-user local processes are inside the trust boundary — no process attestation on loopback; the bearer token gates accidental exposure, not a determined same-user attacker (narrowed by F-3's keychain storage and audit log).
  • Unlocked sections, corpora, and agent memory are plaintext at rest by design — documented and surfaced in the UI; users who need at-rest protection use Locked Sections (which the agent then cannot read at all).
  • The stdio MCP transport trusts its spawner — inherent to stdio; the registration command is user-run, and the HTTP transport is the recommended path.
  • Build-time network is accepted; runtime network is not — model download and dependency installs happen at build, guarded by digests, lockfile integrity, and the cooling window.
  • style-src 'unsafe-inline' remains in the CSP (React/CodeMirror inline styles); script-src is strict, which is where execution risk lives.
  • Remote images in notes no longer load (CSP) — a deliberate tracking-pixel defense, at the cost of remote-image convenience.
  • User-directed file writes are the user's egress, not the app's — export destinations are chosen in native dialogs (the scheduled export's directory once, in main's dialog); a synced destination is moved afterwards by the user's own sync client, and a network-share destination is carried by the OS filesystem layer at the user's direction — the app opens no socket either way. Controls and residuals are assessed in §4.4.

4 Third-party & native code

The Electron analog of a native app's DLL surface is N-API addons + WASM blobs + the Electron runtime itself. Tholos's is small, fully enumerated, and — crucially — the core app runs with zero required native addons: SQLite is Node's built-in node:sqlite, and Argon2id is the pure-JS, audited @noble/hashes.

Process creation is similarly bounded: an execFile of the claude CLI with a fixed argv and no shell, and a utilityProcess.fork of the bundled corpus-index worker with a fixed job shape. The “generate from repo” flow builds a command string for the user to run — Tholos executes nothing.

4.2 Supply-chain controls

  • pnpm-lock.yaml with sha512 integrity for every package; pinned packageManager; CI installs --frozen-lockfile.
  • 7-day cooling-off window on every new package version (minimumReleaseAge) — the standard defense against freshly-poisoned releases.
  • Per-package build-script approvals: dependency postinstalls blocked by default; five deliberately allowed, each with a written reason.
  • Socket Firewall wraps installs; the project itself has no install hooks of any kind.
  • The bundled embedding model is verified against pinned SHA-256 digests at build time, for fresh downloads and cached files alike.
  • Runtime dependency advisories: one remains (sharp/libvips, exposure analysis in the scan appendix); the rest were eliminated by security-floor overrides and the Electron bump.

4.3 Packaging & update channel — the honest gap

Updates come from GitHub Releases via electron-updater: HTTPS transport, sha512 manifest pinning, background download, user-triggered install. Registered as F-1, now closed: releases are CI-built and CI-staged (draft releases on the public feed; publishing is the one human act); Windows installers are Authenticode-signed inside the packaging step via Azure Trusted Signing (short-lived certificates over repo-federated OIDC — no signing key exists to steal; RFC-3161 timestamped so signatures outlive the certificates); and the packaged binary carries embedded asar integrity validation plus asar-only app loading with NODE_OPTIONS/--inspect disabled via Electron fuses. Documented residuals: asar integrity is enforced on Windows/macOS only (Electron implements no Linux validation — a .deb install's tamper evidence is dpkg's install-time checksums), and everything under app.asar.unpacked — the dependency tree plus the app-owned MCP server and converter bundles (unpacked because ELECTRON_RUN_AS_NODE cannot read the asar) — is covered by the installer signature at install time rather than the asar hash. The .deb itself is unsigned (no Linux code-signing analog is wired): Linux update-channel authenticity rests on HTTPS plus a sha512 manifest served from the same feed.

4.4 Runtime network egress — complete list

1. Update check against GitHub Releases on packaged launch. That is the entire list. Fonts are self-hosted; the embedder is pinned allowRemoteModels = false with a bundled model; there is no telemetry, crash reporting, or analytics; the MCP server listens on loopback and originates nothing.

Re-validated 2026-08-24 (issue #242), after the Savings Ledger campaign (ADR-0022) added file exports. The one-channel claim remains literally true — nothing in ADR-0022's feature family opens a socket. But the claim is about runtime network egress, and that category deserves an explicit boundary against a second, distinct category the app has always had: user-directed file writes. Tholos writes files at user-chosen locations — the markdown export and the manual Savings Report export (native save dialogs), and the recurring scheduled Savings Report export (#213) into a directory chosen once in main's native dialog. The one-channel claim is therefore scoped precisely: it inventories network channels opened by application code — Tholos opens no socket and holds no network credential for any export. A chosen destination can still make bytes leave the machine, in two mechanically different ways: a synced folder is written locally and a separate sync client — the user's own infrastructure — moves the bytes afterwards; a UNC or mapped network path makes the OS filesystem layer (e.g. the SMB redirector, using the user's own session credentials) carry Tholos's write over the network as it happens. Both are user-directed egress through paths the user aimed the app at — exactly what the choose-time hint below surfaces — not app-originated channels; neither adds a socket to the inventory above. For the Savings Report the safety property is not the path but the construction: content-free by a schema whitelist enforced at the write boundary (savings-ledger.mjs, named fields only) and again at the export boundary (savings-report.mjs: events rebuilt from named fields, client strings re-sanitized, CSV formula injection neutralized, no dollar amounts) — pinned by tests.

Export-path residuals, assessed (decisions from #242, both implemented):

  • settings.json tamper redirecting the scheduled write — no privilege gained (an attacker with that write access can already write any same-user file; what lands is a content-free report); the Settings status line names the path actually written. Accepted (A2 sits inside the trust boundary, §3.5).
  • Symlink/junction at the target — guard implemented (parity with the F-4 corpus-walk guard): the scheduled writer refuses to write through a symlink planted at its predictable dated filename (assertNotSymlinkTarget, lstat-based, savings-report.mjs; tested). No privilege was gained by the redirect either, but the scheduled write is recurring and unattended — the guard turns a silent redirect into a visible failed status line at one lstat of cost. The chosen directory may itself be a symlink/junction (user intent — the registered-root rule the corpus walker also applies), and the manual export stays unguarded on purpose (its exact path is blessed in the save dialog, overwrite prompt included). The lstat→write gap is an accepted same-user TOCTOU residual.
  • Fixed dated filename, overwrite semantics — a same-day rerun overwrites that day's tholos-savings-report-<date>.json. Deliberate: each file is a full-history snapshot, so the overwritten content is always a strictly older snapshot of the same ledger.
  • UNC/sync-folder hint — implemented (#242): choosing a target that is a UNC path or sits under a well-known sync root (OneDrive, Dropbox, Google Drive, iCloud, Box, Nextcloud/ownCloud, Seafile, Syncthing) shows a one-line, non-blocking heads-up at folder-choose time — “reports written here leave this machine via your own share/sync” (exportDirHint). Inform, never refuse: scheduling to a share is the intended enterprise flow, and the report is content-free either way.

5 MCP / agent access — Rule of Two

Meta's Rule of Two: an agent must not simultaneously hold all three of (a) access to sensitive data, (b) ability to communicate externally, (c) exposure to untrusted input. Tholos grants (a) and (c) in a scoped way and structurally withholds (b): no tool it exposes can reach the network, touch arbitrary files, or execute code. An injected agent can corrupt what it can write (mitigated by undo snapshots, the audit log, and opt-in scope) but cannot use Tholos as an exfiltration or execution channel.

One caveat the tool-shaped argument doesn't cover, closed as F-6 (ADR-0020): persisted content is a deferred channel — an injected agent can write a link whose URL encodes note data (https://…?d=…, mailto:?body=…) into a Page and wait for a human click. Mitigated at the actual egress moment: every external open shows the full URL in an in-app confirmation (default on) before the OS is invoked, and agent writes that introduce new external links are flagged on the page banner and counted (count only, never URLs or hosts) in the audit log.

5.1 Transports

  • Streamable HTTP (recommended) — in-process, 127.0.0.1 only, single /mcp POST endpoint. Gates, in order: bearer token (256-bit random, constant-time compare, 401 before any parsing), DNS-rebinding protection, no CORS, 4 MiB body cap, stateless per-request server instances. Off by default; every tool call lands in the append-only audit log.
  • stdio (legacy/fallback) — a separate process registered via claude mcp add; trusts its spawner (accepted risk §3.5) and receives a smaller surface: no memory tools, no reindex.

5.3 Scoping & gating

  • Agent Access is per-section, off by default, enforced on every call in the gateway — not in the UI.
  • Locked Sections are excluded by construction (O7): the gateway holds no key session, so agent-facing reads of encrypted rows are impossible, not merely forbidden.
  • Agent memory is off by default and enforced per-call with a live settings read, so disabling it takes effect immediately.
  • Embeddings are local-only by construction — remote model fetch disabled in every process that embeds.
  • Every HTTP tool call is audited (F-3): timestamp, transport, tool, target ids, outcome — never content — appended to userData/mcp-audit.log. The legacy stdio transport is not audited: it inherently trusts its spawner (accepted risk §3.5).

5.4 Candid limitations (all registered)

  • Memory/persona persistence is a prompt-injection channel — by design, and it remains one: content laundered from an untrusted corpus into save_memory still persists and still re-enters context in later sessions; that is what agent memory is, and no mitigation prevents the write or the recall. What the memory-integrity campaign (ADR-0021) closed is the channel's forgeability, invisibility, and irreversibility — attribution, visibility, and recovery, not prevention: provenance is server-stamped (each write path stamps its own caller's identity in main; 'user' is a reserved origin an agent cannot claim, a smuggled origin argument is silently corrected — the Settings audit surface shows evidence, not claims); agent Persona rewrites are recoverable and visible (one-deep Persona Snapshot rolled inside the concurrency guard; an accumulated rewrite notice in Settings and as a main-window banner, cleared only by user acts — an injected agent cannot neutralize its own flag); memory/persona writes get the F-6 link flagging (the ADR-0020 scanner in strict plain-text mode — code fences exempt nothing — counted into the audit log, invisible to the agent); forgetting is recoverable (30-day tombstone with Restore; “Clear all” stays immediate); and recall is fenced (results lead with a structural stored-data notice plus per-item provenance). Residuals: the persistence and recall themselves remain — accepted, bounded by the off-by-default opt-in, size caps, and the visibility and recovery above; pre-campaign memories keep whatever origin they were saved with; no per-memory review banner (durable audit evidence only); fencing is advisory — the load-bearing mitigations are provenance, versioning, and visibility.
  • create_section self-grants Agent Access to sections the agent itself creates — a bounded, visible expansion.
  • Corpus chunk text is returned verbatim, unfenced — injection-aware clients should treat it as data.
  • Where no OS keychain exists (a bare Linux session), bearer-token storage falls back to plaintext — surfaced in Settings, not silent.
  • Persisted links are a deferred egress channel (F-6, ADR-0020): closed at click time (full-URL confirmation, default on) and made visible at write time (banner + audit count). The same flagging now covers memory and persona writes (ADR-0021) — in a strict plain-text scan mode, so a code fence is not a bypass. Residuals: the preference can be deliberately turned off; a lookalike URL still relies on the user reading the dialog.

Envelopev2 (ADR-0019): ver(0x02) ‖ iv ‖ tag ‖ ct with the envelope's section/page/field address as GCM AAD; Argon2id cost stored per section, validated + bounded before deriving. Legacy v1 is read-only and migrates on first unlock

Randomnessnode:crypto only; no Math.random() anywhere in src/

Correctness is exercised by the unit suite and by property fuzzing: round-trip fidelity, any bit flip anywhere in the envelope throws, truncation at every byte offset throws, wrong keys throw, and the canary check is total.

F-2 improvements — implemented (ADR-0019): an envelope version byte with per-section stored KDF params (crypto agility; validated and bounded before deriving, since stored params are unauthenticated by construction), AAD binding each envelope to its section/page/field address (intra-section envelope transplants fail the auth tag), and verified residue scrubbing (secure_delete + checkpoint/VACUUM with a persisted retry marker) after plaintext→ciphertext transitions. v1 sections migrate lazily on first unlock. Documented residuals: same-address replay, filesystem-level remanence, and an app downgrade reading migrated sections as “wrong passphrase” until re-upgraded.

9 Ongoing assurance

  • Every PR: the full node --test suite (~790 tests) including deterministic property-fuzz suites — extractors (random bytes + mutated real documents), markdown render (no-executable-foothold + ReDoS bounds), crypto envelope (tamper totality), smart-paste, MCP endpoint (auth-before-parse, garbage tolerance) — plus a 30-second-per-target coverage-guided fuzz smoke (Jazzer.js/libFuzzer, seeded from real fixture documents).
  • Nightly: 10 minutes of coverage-guided fuzzing per target; crashing inputs uploaded as reproducer artifacts, failures loud.
  • Harness honesty: each harness was validated against a planted bug before being trusted; the planted-bug experiment also showed pure-random fuzzing misses narrow conditions that seeded mutation catches — which is why both tiers exist.
  • Upstream fuzzing: the memory-unsafe parsing surfaces Tholos delegates to — PDFium and libvips — are continuously fuzzed on Google's OSS-Fuzz; Tholos's own parsers are memory-safe JS.
  • Dependency hygiene, continuously: frozen lockfile in CI, 7-day cooling window, build-script approvals, guarded installs, pnpm audit with a written triage discipline.
